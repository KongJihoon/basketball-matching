# UserService 인터페이스 제거

## 문제 상황

기존 구조는 UserService 인터페이스와 UserServiceImpl 구현체로 나뉘어 있었다.

그러나 실제 구현체는 하나였고 다음 요구사항도 없었다.
- 구현체 교체
- 외부 시스템별 구현 분리
- 여러 구현체 제공

인터페이스가 확장 지점으로 사용되기보다 파일과 탐색 단계만 증가시키고 있었다.

---

## 선택지

### 선택지 1: 인터페이스와 구현체 유지

장점:

- 향후 구현체 추가에 유리하다.
- 구현에 대한 의존을 줄일 수 있다.

단점:

- 현재 존재하지 않는 확장 가능성을 위해 구조가 복잡해진다.
- 서비스 코드를 찾을 때 인터페이스와 구현체를 오가야 한다.
- 구현체가 하나인 상태에서는 실질적인 이점이 작다.

### 선택지 2: 구체 서비스 클래스 사용

장점:

- 구조가 단순해진다.
- 클래스 탐색이 쉬워진다.
- 현재 요구사항에 필요한 만큼만 추상화한다.

단점:

- 향후 여러 구현체가 필요하면 인터페이스를 다시 추출해야 한다.

---

## 결정

UserService 인터페이스와 UserServiceImpl 구조를 제거하고,
UserService 구체 클래스를 Spring Service로 사용한다.

### 결정 이유

인터페이스는 서비스 클래스마다 기계적으로 만드는 것이 아니라,
실제로 여러 구현체를 교체하거나 명확한 경계를 제공해야 할 때 도입하는 것이 적절하다고 판단했다.

필요해지는 시점에 인터페이스를 추출하는 비용이
현재 불필요한 추상화를 계속 유지하는 비용보다 작다고 판단했다.

---

## 결과
- UserServiceImpl 제거
- UserService가 직접 서비스 구현을 담당.
