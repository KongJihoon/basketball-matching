# 초기 서비스 범위에서 경기 랭크와 참가자 평가 기능 제거

## 문제 상황

기존 프로젝트에는 경기 종료 후 참가자를 평가하고, 평균 점수에 따라 사용자 랭크를 계산하는 기능이 존재했다.

관련 기능은 다음과 같다.
- 경기 참가자 평가
- 사용자 평균 점수 조회
- 사용자 레벨 계산
- 레벨 엔티티 및 Repository
- 경기 상세 및 목록의 사용자 레벨 표시

다양한 기술과 기능을 경험할 수 있다는 장점은 있었지만, 초기 서비스 관점에서는 다음 문제가 있었다.

### 충분한 사용자와 평가 데이터가 필요함

랭크가 의미 있으려면 다음 조건이 필요하다.

- 반복적으로 경기에 참가하는 사용자
- 충분한 평가 횟수
- 평가하지 않은 사용자 처리 정책
- 악의적인 낮은 평가 방지
- 지인끼리 점수를 올리는 행위 방지
- 포지션과 경기 수준을 고려한 평가 기준

초기 서비스는 사용자와 경기 데이터가 충분하지 않으므로
점수와 랭크의 신뢰성을 보장하기 어렵다.

### 핵심 기능과의 관련성이 낮다.

서비스의 핵심 목적은 다음과 같다.

```text
원하는 경기 검색
→ 경기 참가
→ 실제 경기 진행
```
랭크와 평가는 핵심 매칭 흐름이 안정화된 이후
사용자 신뢰도를 보완하는 기능에 가깝다.

초기 단계에서 랭크 기능을 유지하면
핵심 기능보다 부가 기능의 코드와 정책이 더 복잡해질 수 있다.

### 운영 정책 부족
기존 구현에는 다음 정책이 충분히 정의되어 있었다.

- 자신을 평가할 수 있는지
- 경기 생성자를 평가할 수 있는지
- 한 사용자를 여러 번 평가할 수 있는지
- 경기 불참 사용자를 평가할 수 있는지
- 평가 수정과 삭제가 가능한지
- 신고된 평가를 어떻게 처리할지
- 평가 조작을 어떻게 방지할지

정책이 없는 상태에서 점수만 계산하면
기술적으로 동작해도 실제 서비스에서 신뢰하기 어렵다.

## 선택지

### 선택지 1. 기존 랭크와 평가 기능 유지

#### 장점
- 프로젝트 기능 수가 많아 보인다.
- 집계 쿼리와 점수 계산을 경험할 수 있다.
- 사용자 신뢰도를 표시할 수 있다.
  
#### 단점
- 평가 데이터가 적으면 랭크가 의미 없다.
- 평가 조작과 악성 평가 정책이 필요하다.
- 핵심 매칭 기능의 복잡도가 증가한다.
- 사용하지 않는 엔티티와 서비스가 계속 유지된다.
- 기능의 존재 이유를 면접에서 설명하기 어렵다.

### 선택지 2. 초기 범위에서 제거하고 필요할 때 다시 설계

#### 장점
- 핵심 경기 매칭 흐름에 집중할 수 있다.
- 불필요한 엔티티와 서비스가 제거된다.
- 현재 요구사항에 맞는 단순한 모델을 유지할 수 있다.
- 데이터가 쌓인 이후 실제 요구를 기준으로 다시 설계할 수 있다.
- 프로젝트의 기술 선택을 제품 관점에서 설명할 수 있다.
  
#### 단점
- 기존에 구현한 기능과 코드가 제거된다.
- 사용자 신뢰도를 표현하는 수단이 줄어든다.
- 평가와 집계 기능 경험을 현재 버전에서 보여주기 어렵다.

## 결정

초기 서비스 범위에서는 경기 랭크와 참가자 평가 기능을 제거한다.

다음 코드를 제거했다.
```text
LevelEntity
LevelRepository
LevelQueryRepository
EvaluationService
EvaluationServiceImpl
UserLevelService
GameUserLevel
EvaluatePlayerDto
GameAvgScoreDto
GameUserLevelDto
```

UserEntity, GameDetailResponse, GameListResponse에서도
랭크와 레벨 관련 필드를 제거한다.
기능이 많아 보이는 것보다 현재 서비스에 필요한 기능이 명확하고, 각 기능의 정책을 설명할 수 있는 것을 우선한다.

---

## 대체 방향

랭크 기능을 제거했다고 해서 통계와 사용자 경험 개선을 포기한것은 아니다.

경기 데이터가 쌓이고 기존 기능이 견고해지면 다음 기능을 검토할 수 있다.
- 경기 조회수
- 인기 경기 목록
- 지역별 경기 생성 통계
- 시간대별 경기 참가율
- 경기 형식별 모집 마감률
- 참가 취소율
- 경기 생성 후 마감까지 걸린 시간

이 데이터는 실제 사용자의 행동을 기반으로 하므로
초기 평가 점수보다 서비스 개선에 활용하기 쉽다.
통계 조회에 성능 문제가 발생하면 다음 과정을 적용할 수 있다.

## 결과
- 랭크 및 평가 관련 엔티티와 서비스 제거
- UserEntity의 레벨 의존성 제거
- 경기 응답 DTO의 불필요한 레벨 정보 제거
- 경기 패키지 구조 단순화
- 핵심 매칭 기능의 책임과 정책에 집중
- 초기 서비스에 필요한 기능과 후속 기능을 구분
- 기능 추가뿐 아니라 제거도 설계 결정이라는 근거 기록
