# 경기 참가를 선착순 즉시 확정 방식으로 변경

## 문제 상황

기존 경기 참가 흐름은 다음과 같았다.
```text
사용자 참가 신청
→ APPLY 상태 저장
→ 경기 생성자가 신청자 조회
→ 승인 또는 거절
→ ACCEPT 또는 REJECT 상태 저장
```

이 구조는 경기 생성자가 참가자를 심사해야 하는 서비스에서는 의미가 있다.
예를 들어, 현재 경기 신청 구조에 결제 기능을 추가한다면 승인과 요청의 상태가 필요할 것이다.

하지만 현재 프로젝트에는 다음 기능과 정책이 존재하지 않는다.
- 참가비 결제
- 사용자 자격 심사
- 팀 전력 조정을 위한 승인 기준
- 참가 신청 만료
- 승인 대기 시간 제한
- 승인과 거절에 대한 명확한 판단 기준

경기 생성자는 특별한 기준 없이 참가자를 승인해야 했고, 사용자는 정원이 남아 있어도 승일될 때까지 기다려야 한다.

승인 정책의 필요성보다 다음 코드 복잡도가 더 크게 발생했다.
- 신청 API
- 신청자 목록 API
- 승인 API
- 거절 API
- 승인 및 거절 서비스
- APPLY, REJECT 상태
- 승인 전후 참가 인원 처리

---

## 선택지

### 선택지 1. 참가 신청 후 경기 생성자 승인

#### 장점
- 경기 생성자가 참가자를 사전에 확인할 수 있다.
- 사용자 성향이나 실력에 따라 참가 여부를 결정할 수 있다.
- 결제나 별도 심사 기능이 추가될 때 확장하기 쉽다.
  
#### 단점
- 승인 기준이 없다면 형식적인 절차가 된다.
- 사용자가 승인될 때까지 기다려야 한다.
- 경기 생성자가 모든 신청을 확인해야 한다.
- 신청, 승인, 거절 API와 상태 관리가 필요하다.
- 승인되지 않은 신청의 만료 정책이 필요하다.
- 서비스와 테스트의 상태 분기가 많아진다.

### 선택지 2. 선착순 즉시 참가

#### 장점
- 정원이 남아 있으면 즉시 참가할 수 있다.
- 사용자 흐름이 단순해진다.
- APPLY, REJECT 상태와 승인 API를 제거할 수 있다.
- 참가 가능 여부를 한 번의 트랜잭션에서 판단할 수 있다.
- 현재 프로젝트의 핵심인 빠른 경기 매칭에 적합하다.
  
#### 단점
- 경기 생성자가 참가자를 미리 선별할 수 없다.
- 악성 사용자를 사전에 차단할 정책이 필요하다.
- 마지막 정원에 동시 요청이 발생하면 정원 초과 가능성이 있다.
- 참가 이후 강퇴 기능과 알림 정책이 중요해진다.

## 결정

현재 프로젝트에서는 선착순 즉시 참가 확정 방식을 사용한다.
사용자가 참가 조건을 만족하면 참가 요청과 동시에 `ParticipantGameStatus.ACCEPT` 상태로 변경한다.

```text
참가 가능 여부 검증
→ ParticipantGameEntity 생성
→ ACCEPT 상태 전이
→ 경기 참가 인원 증가
```

다음 기능은 제거한다.
- APPLY 상태
- REJECT 상태
- 경기 생성자의 참가 승인
- 경기 생성자의 참가 거절
- 승인 대기 목록
  
경기 생성자는 참가자를 사전에 승인하지 않지만,
블랙리스트 사용자의 참가를 차단하고
경기 시작 1시간 전까지 참가자를 강퇴할 수 있다.

---

## 상태 정책
```text
ACCEPT
CANCEL
KICKOUT
DELETE
```

허용하는 주요 상태 전이는 다음과 같다.
```text
신규 참가:      null → ACCEPT
참가 취소:      ACCEPT → CANCEL
취소 후 재참가: CANCEL → ACCEPT
참가자 강퇴:    ACCEPT → KICKOUT
경기 삭제:      ACCEPT → DELETE
```

---

## 동시성 트레이드 오프

현재 참가 가능 여부는 다음 순서로 검증된다.
```text
현재 참가 인원 확인
→ 정원 확인
→ 참가 상태 ACCEPT 변경
→ 참가 인원 증가
```

동시에 여러 요청이 마지막 한 자리를 확인하면 두 요청이 모두 참가 가능하다고 판단할 수 있다.

따라서 선착순 정책을 선택했다고 해서 코드 실행 순서만으로 실제 선착순이 보장되는 것은 아니다.

다음 단계에서 동시 요청을 재현한 후 해결 방식을 비교한다.
- DB 유일 제약조건
- 낙관적 락
- 비관적 락
- 조건부 UPDATE
- 분산 환경이 필요한 경우 Redis 기반 락
  
측정과 재현 없이 특정 락을 먼저 적용하지 않는다.

## 결과
- 참가 요청 즉시 참가 확정
- 승인 대기 시간 제거
- 참가 승인 및 거절 API 제거
- APPLY, REJECT 상태 제거
- 참가 상태 전이 규칙 단순화
- 참가 상태와 경기 인원 변경 책임 통합
- 동시성 문제가 발생할 수 있는 지점 명확화
- 향후 결제나 심사 정책이 추가되면 승인형 구조 재검토
