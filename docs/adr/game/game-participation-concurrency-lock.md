# 경기 참가 동시성 제어에 비관적 락 사용

## 문제 상황

정원 6명인 경기에 생성자 1명이 참가한 상태에서 일반 사용자 100명이 동시에 참가하면, 락이 없는 구현은 12건을 성공시켜 실제 `ACCEPT`가 13명까지 증가했다. 경기의 `participant_count`는 6으로 남아 실제 참가 데이터와 7명 차이가 발생했고 HTTP 시스템 오류도 36건 발생했다.

경기 참가 기능은 다음 불변식을 반드시 지켜야 한다.

```text
participant_count = 실제 ACCEPT 수
실제 ACCEPT 수 <= head_count
남은 5자리에는 정확히 5명만 참가 성공
정원 초과 요청은 FULL_HEADCOUNT_GAME으로 정상 거절
```

## 선택지

### 락 없이 처리

구현은 단순하지만 여러 트랜잭션이 같은 이전 참가 인원 값을 읽어 초과 승인, 유실 갱신과 시스템 오류가 발생했다. 핵심 불변식을 지키지 못하므로 사용할 수 없다.

### 낙관적 락과 무재시도

`@Version`으로 커밋 시점의 변경 충돌을 감지한다. 100명 동시 참가에서 성공 5건, 실제 `ACCEPT` 6명, 초과 승인 0명을 달성해 DB 정합성은 지켰다.

그러나 HTTP 테스트에서 정원 초과 정상 거절은 56건에 그쳤고 39건이 시스템 오류로 종료됐다. 낙관적 락은 충돌을 감지할 뿐 정상 응답으로 복구하지 않으므로 현재 API 계약을 만족하지 못했다.

### 낙관적 락과 제한된 재시도

충돌 시 새 트랜잭션에서 다시 조회하면 최신 정원을 기준으로 성공 또는 정상 거절에 도달할 수 있다. 하지만 최대 시도 횟수, 백오프, 재시도 소진 응답, 트랜잭션 프록시 경계와 멱등성을 추가로 설계해야 한다.

이번 선착순 시나리오는 5자리에 100명이 요청해 충돌이 예외적이지 않고 지배적으로 발생한다. 대부분의 재시도는 최신 상태를 다시 읽은 뒤 정원 초과로 거절하기 위한 비용이 된다.

### 비관적 쓰기 락

경기 행을 조회할 때 `PESSIMISTIC_WRITE`를 사용해 같은 경기의 참가 변경을 순서화한다. 대기 시간과 DB 락 의존성이 생기지만, 충돌이 빈번한 짧은 임계 구역에서 구현과 실패 모델이 단순하다.

## 결정

경기 참가에는 비관적 쓰기 락을 사용한다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("""
        select g
        from GameEntity g
        where g.gameId = :gameId
        and g.deletedDateTime is null
        """)
Optional<GameEntity> findActiveGameWithPessimisticLock(
        @Param("gameId") Long gameId
);
```

서비스의 기존 `@Transactional` 범위 안에서 경기 행을 잠그고, 락을 얻은 트랜잭션이 커밋된 최신 참가 인원과 경기 상태를 검증한다.

## 결과

| 항목 | 락 없음 | 낙관적 락 무재시도 | 비관적 락 |
|---|---:|---:|---:|
| 참가 성공 | 12건 | 5건 | 5건 |
| 정상 정원 초과 | 52건 | 56건 | 95건 |
| 시스템 오류 | 36건 | 39건 | 0건 |
| 실제 `ACCEPT` | 13명 | 6명 | 6명 |
| 초과 승인 | 7명 | 0명 | 0명 |
| DB 정합성 | `FAIL` | `PASS` | `PASS` |

비관적 락은 CountDownLatch 통합 테스트와 k6 3회 반복 측정에서 매번 성공 5건, 정상 거절 95건, 시스템 오류 0건을 기록했다.

선택 후 요청 규모를 200, 500, 1,000 VU로 높인 추가 검증에서도 모든 단계가 DB 정합성 `PASS`, 시스템 오류 0건을 기록했다. 1,000 VU의 참가 API p95는 2,024.20ms였고 HikariCP Pending Connection은 최대 198까지 증가했지만 Connection Timeout은 발생하지 않았다.

이 결과는 로컬 단일 서버에서 검증한 상한이다. 실제 운영 수용량이나 시스템의 절대 파괴 지점을 의미하지 않으며, 요청 규모가 커질수록 비관적 락의 대기시간이 증가하는 트레이드오프도 확인했다.

## 트레이드오프와 재검토 조건

같은 경기의 참가 요청은 락을 얻을 때까지 대기하므로 인기 경기에 요청이 집중되면 지연시간과 DB 커넥션 점유 시간이 증가할 수 있다. 트랜잭션 안에서 외부 API 호출이나 오래 걸리는 작업을 수행하지 않고 락 보유 시간을 짧게 유지해야 한다.

다음 상황이 관측되면 현재 결정을 다시 검토한다.

- 락 대기 또는 타임아웃이 지속적으로 발생한다.
- 특정 인기 경기에 요청이 집중돼 처리량 요구를 충족하지 못한다.
- DB 다중화 구조에서 동일한 잠금 보장을 유지하기 어렵다.
- 대기열, Redis 분산 락 또는 비동기 참가 처리의 필요성이 생긴다.
