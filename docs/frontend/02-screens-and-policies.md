## 2. 공통 동작

- 데이터 요청: 최초 로딩 skeleton, 정상, 빈 결과, 재조회 중, 네트워크 오류를 구분한다. 백그라운드 재조회 중 기존 데이터를 유지한다.
- 폼: 라벨·필수 표시·도움말·필드 오류 제공, 실패해도 입력값 보존, 중복 제출 방지, 첫 오류에 포커스.
- 인증 요구: 비회원의 참가 버튼은 로그인 안내, 로그인 후 내부 `returnTo`로 복귀. 이미 참가한 상태인지 서버에서 재확인한다.
- 401: 만료 코드인 경우에만 인증 모듈을 통한 단일 갱신. 실패 시 세션 정리·로그인 안내. 403 업무 거절과 제재는 별도 메시지.
- 확인 모달: 대상 이름·행동·결과를 명시한다. 성공 전 모달을 닫고 완료했다고 표시하지 않는다.
- 과거 시각/시간 제한: 프론트는 안내하고 서버 응답이 최종 기준이다. Asia/Seoul 기준 날짜·시각을 사용한다.

## 3. S-01 경기 찾기

데스크톱은 헤더 → 서비스 탐색 → 소개 배너 → 좌측 필터 / 우측 날짜·정렬·목록 순서다. 모바일은 헤더 → 간결한 소개 → 날짜 스트립 → 필터 버튼·정렬 → 목록이다. 상세 시각 구조는 [디자인 가이드](04-design-system.md)를 따른다.

| UI | API/저장 값 | 동작 |
| --- | --- | --- |
| 날짜 스트립·달력 | `date=YYYY-MM-DD` | 선택 날짜 변경 시 page=0 |
| 전체 예정 | date 생략 | 과거를 제외한 서버 기본 검색 |
| 지역 | `cityName` | 시도 단일 선택, 기본 전체 |
| 검색 | `keyword` | 제목/장소 검색, 50자 이내, 제출 시 적용 |
| 형식 | `matchFormat` | 전체/3대3/5대5 단일 선택 |
| 실내외 | `fieldStatus` | 전체/실내/실외 단일 선택 |
| 성별 조건 | `matchGenderType` | 전체/남성/여성/혼성 |
| 모집 | `gameStatus` | 전체/모집 중/마감 |
| 정렬 | `sortType` | 시작 빠른순/최신순 |
| 페이지 | `page`, `size` | 기본 page=0, size=10 |

초기 진입에는 서울 오늘 날짜를 URL에 반영한다. 이 기본값은 제품 설계 결정이며 서버가 기본 지역을 서울로 제한한다는 뜻은 아니다. 사용자가 지역 전체 또는 전체 예정을 선택하면 해당 파라미터를 제거한다. URL의 유효한 값이 초기 기본값보다 우선한다. 잘못된 enum·음수 페이지·잘못된 날짜는 요청 전 정규화하고 URL을 replace한다. 존재하지 않는 달력 날짜도 거부한다.

모바일 필터 시트는 임시 선택을 보관하고 `적용` 시 URL에 일괄 반영한다. `초기화`는 필터를 전체로 되돌리며 날짜 선택은 유지한다. 날짜/필터/정렬 변경은 항상 페이지를 초기화한다. 브라우저 뒤로 가기로 이전 조건을 복원한다.

목록 항목은 시작 시각, 제목, 장소, 주소, 형식·성별, 참가/정원, 모집 배지를 표시하고 상세로 연결한다. 현재 목록 DTO에 실내외·좌표·종료 시각·사진은 없으므로 목록에서 이를 임의로 표시하거나 항목마다 상세 API를 추가 호출하지 않는다. 결과 0건에는 `필터 초기화`를 제공한다. 전체 건수는 Page의 totalElements를 사용한다.

## 4. S-02 상세와 액션

### 4.1 읽기 영역

제목·모집 배지·예정/진행/종료 표시, 시작/종료 시각, 장소·전체 주소, 형식·성별·실내외, 참가 인원, 생성자 닉네임, 본문을 표시한다. 본문은 plain text로 렌더링하고 줄바꿈을 보존한다. 좌표가 없어도 주소 정보는 정상 표시한다.

참가자 명단은 확정 참가자만 요청한다. 명단은 닉네임·포지션·생성자 배지를 표시하며 페이지 단위로 조회한다. 타인의 이메일·전화·생년월일을 표시하지 않는다.

### 4.2 버튼 결정 표

아래의 내 참가 상태는 [B-02 보완](03-api-integration.md#8-백엔드-보완-작업)이 필요하다. 아직 모르는 상태를 미참가로 간주하지 않는다.

| 사용자 관계 | 기본 액션 | 제한 |
| --- | --- | --- |
| 비회원 | 로그인하고 참가 | 마감/시각 경과 시 모집 종료 안내 |
| USER·미참가 | 참가하기 | 시작 30분 전보다 이전, 여석·성별 조건 |
| USER·ACCEPT | 참가 취소, 참가자 보기 | 취소는 시작 30분 전보다 이전 |
| USER·CANCEL | 다시 참가 | 신규 참가와 동일 조건 |
| USER·KICKOUT | 재참가 불가 안내 | 참가 액션 비활성 |
| 생성자 | 참가자 보기, 수정, 삭제 | 참가·참가 취소 없음 |
| ADMIN | 상세 읽기, 관리자 탐색 | USER 액션 노출 없음 |

생성자의 수정은 시작 24시간 전보다 이전, 삭제와 다른 참가자 강퇴는 시작 1시간 전보다 이전이다. 자기 자신 강퇴는 제공하지 않는다. 참가자 강퇴 요청에는 사용자 ID가 아닌 `participationId`를 전달한다.

참가 확인 모달에는 일시·장소·참가 조건을 표시한다. `FULL_HEADCOUNT_GAME`/`ALREADY_ACCEPT_USER` 등 실패 시 관련 상세·내 참가 상태를 재조회한다. 404는 삭제/없음 안내와 목록 복귀를 제공한다.

## 5. S-03·S-04 경기 폼

| 필드 | 생성 | 수정 | 검증/안내 |
| --- | --- | --- | --- |
| 제목·내용 | 필수 | 변경분만 | UI 기본 제목 100·내용 255자, 서버 생성 제약 통일 B-09 필요 |
| 정원 | 필수 | 가능 | 3대3 6~100, 5대5 10~100, 수정은 현 참가자 수 이상 |
| 형식·참가 성별 | 필수 | 조건부 | 생성자 외 참가자가 있으면 변경 불가 |
| 실내외 | 필수 | 변경 불가 | 수정 화면에는 읽기 전용 |
| 시작·종료 | 필수 | 두 값을 함께 | 시작≥현재+24시간, 종료>시작, 길이 60~240분 |
| 장소명·주소 | 필수 | 변경 불가 | 주소의 첫 단어는 지원 시도 정식 명칭 |
| 위도·경도 | 선택 | 변경 불가 | MVP 직접 입력 UI 없음. 외부 장소 선택 기능 도입 시 연결 |

생성 성공 후 상세로 이동하고 본인 자동 참가를 안내한다. 수정은 실제 변경된 필드만 보내고, 시각 변경 시 두 필드를 함께 보낸다. 변경이 없으면 저장 버튼을 비활성화한다. 편집 중 정책이 달라져 서버가 거절하면 입력값을 유지하고 최신 조건을 조회한다.

동일 장소 시간 중복은 서버가 판정한다. 생성자가 해당 성별 조건을 만족해야 하는지 등 코드에 없는 추가 정책을 임의로 강제하지 않는다.

## 6. S-05~S-09 인증 화면

### 이메일 로그인

이메일·비밀번호, 로그인 버튼, 카카오 시작, 회원가입·비밀번호 재설정 링크를 제공한다. 성공 후 USER는 returnTo 또는 내 경기, ADMIN은 관리자 신고로 이동한다. 잘못된 비밀번호는 서버 업무 오류이며 토큰 갱신 대상이 아니다.

### 회원가입

1. 이메일 입력·사용 가능 확인 → 인증번호 요청(202 접수).
2. 6자리 코드 확인 → 이메일 인증 완료.
3. 비밀번호·확인, 닉네임·중복 확인, 이름, 생년월일, 전화, 전체 주소, 포지션·성별 입력.
4. 가입 201 성공 → 로그인 화면으로 이동.

이메일을 바꾸면 화면의 인증 완료 표시를 해제한다. 인증번호 만료 3분과 인증 완료 후 가입 가능 10분을 안내하되, 서버 응답에 만료 시각이 없으므로 타이머는 보조 안내로 취급한다. 발송 성공 문구는 `인증번호를 요청했습니다. 이메일을 확인해 주세요.`로 한다. 재요청 버튼은 UI에서 30초 간격을 두는 기본안을 사용하되 이는 서버 요청 제한을 대신하지 않는다.

닉네임은 2~12자, 비밀번호는 영문·숫자·허용 특수문자 `~!@#$%^&*()`를 포함한 8자 이상, 전화는 서버의 `01[016789]-숫자3~4자리-숫자4자리` 형식을 따른다. 생년월일은 현재 서버에서 필수 여부만 검증하므로 과거 날짜 강제는 B-09 정책 확인 대상으로 둔다. `NONE` 성별은 B-08 결정 전 일반 가입 선택지에서 노출을 보류하되 서버의 기존 NONE 계정도 고려한다.

### 비밀번호 재설정·변경

재설정은 이메일→코드 확인→새 비밀번호/확인→완료로 구성한다. 프로필의 변경은 현재 비밀번호·새 비밀번호·새 비밀번호 확인을 받는다. 필드명이 서로 다르므로 API 명세를 따른다. 카카오 사용자의 비밀번호 메뉴는 로그인 방식 계약 B-05 완료 후 분기한다.

### 카카오

인가 시작은 페이지 이동이다. 콜백 복귀/일회용 티켓·flowType 전달은 B-01 계약 완료 후 구현한다. SIGNUP은 비밀번호 없이 이름·닉네임·생년월일·전화·주소·포지션·성별을 받는다. 티켓 만료/이미 소비/가입 실패 시 재시작 안내를 제공한다. StrictMode나 새로고침으로 티켓을 중복 교환하지 않는다.

## 7. S-10~S-12 내 경기·계정·알림

내 경기는 예정/종료 탭과 각 페이지 상태를 URL로 보존한다. 진행 중 공백은 B-03에서 해소한 뒤 예정 탭 안에 `진행 중` 표시로 제공하는 안을 기본으로 한다. 종료 경기에서는 참가자 목록과 신고를 연결한다. 신고 모달은 대상 닉네임, 유형, 500자 이내 내용, 중복 제출 방지를 갖춘다. 자기 자신은 대상에서 제외한다.

프로필에서 이름·이메일·생년월일은 읽기 전용, 닉네임·전화·주소·성별·포지션만 편집한다. 탈퇴 확인에는 예정 경기/참가 관계 정리와 세션 종료를 안내하고 성공 시 사용자 캐시·토큰·SSE를 정리한다. 현재 시점 이후 경기의 정리만 구현되어 있으므로 전체 이력 삭제라고 표현하지 않는다.

알림은 읽지 않은 항목·유형·내용·시각과 `읽음` 액션을 표시한다. 서버에 총 미확인 수가 없으므로 일부 페이지 길이를 전체 개수처럼 배지에 표시하지 않는다. 읽음 처리로 항목이 빠지면 현재 페이지를 재조회한다. 초기 목록은 size=20, 이전/다음 탐색을 제공하며 다음 페이지가 빈 경우 끝 안내를 표시한다. 빈 응답을 받은 페이지까지 허용하는 방식임을 구현에 명시한다.

기존 영속 알림에는 이동 대상 ID가 없으므로 B-04 완료 전에는 메시지 확인·읽음만 제공한다. 읽음 처리와 상세 이동은 별도 액션으로 정의해 사용자의 의도와 다른 읽음 처리를 피한다. 실시간 경기 생성 메시지는 생성 완료 안내로 처리하고 DB 미확인 알림 수에 더하지 않는다.

## 8. S-13·S-14 관리자

신고는 대기/승인/거절 탭, 페이지, 경기·신고자·대상·유형·내용·접수일·검토 결과를 표시한다. 대기 상태에서만 승인/거절 버튼과 필수 사유(500자 이하)를 제공한다. 승인된 신고에는 별도의 `7일 제재 적용` 확인 모달을 둔다.

제재 모달은 대상과 신고 근거, 7일 기간, 예정 경기 정리·접근 제한을 안내한다. 성공 후 응답의 실제 만료 시각을 표시한다. 기존 신고 목록에 제재 완료 여부가 없으므로 제재 버튼 노출만으로 적용 가능하다고 보장하지 않고 재사용·활성 제재 오류를 처리한다. 초기에는 제재 목록 링크와 서버 검증을 사용한다.

제재 목록은 ACTIVE/EXPIRED, 대상 닉네임·이메일, 적용/만료 시각, 근거 신고 ID를 표시한다. 해제·기간 변경 API는 없으므로 해당 버튼은 만들지 않는다. 독립 신고 상세 조회 API도 없으므로 검토 상세는 조회한 목록 행의 패널로 시작한다.

## 9. 시간 경계 표

| 행위 | 허용 | 경계 시각에서 결과 |
| --- | --- | --- |
| 생성의 시작 시각 | now+24시간 이상 | 정확히 24시간 이후 허용 |
| 수정 | now < 기존 start-24시간 | 정확히 24시간 전 거절 |
| 참가·참가 취소 | now < start-30분 | 정확히 30분 전 거절 |
| 삭제·강퇴 | now < start-1시간 | 정확히 1시간 전 거절 |
| 신고 | end ≤ now ≤ end+7일 | 종료 시각·7일째 경계는 허용 |

여석·성별·권한·참가 상태 등 다른 조건도 함께 충족해야 한다. 같은 오류가 다른 순서의 서버 검증에서 발생할 수 있으므로 프론트가 특정 오류 하나만 기대하지 않는다.
