# 서비스 범위·MVP 기획서

작성일: 2026-11-04 · 상태: 구현 기준 초안 v1

## 1. 목적과 문서의 기준

개인 사용자가 날짜·지역·경기 조건에 맞는 농구 경기를 찾고 선착순으로 참가하며, 생성자가 일정과 참가자를 관리할 수 있는 웹 서비스를 만든다. 기존 Spring Boot의 정책과 데이터를 화면에 연결하는 것이 첫 목표다.

디자인 참고 기준은 사용자가 지정한 [플랩풋볼 구장 예약 화면](https://www.plabfootball.com/?date=2026-11-09&tab=stadium)이다. 2026-11-04 브라우저에서 확인한 상단 탐색·넓은 배너·날짜 선택·필터·목록 구조를 농구 매칭에 맞게 적용한다. 구장 대관 사업을 추가하는 요구로 해석하지 않는다. 디자인 적용 세부 기준은 [디자인 가이드](04-design-system.md)에 기록한다.

현재 구현 사실과 프론트 설계 결정은 구분한다. 이 문서의 MVP·경로·레이아웃은 제안된 구현 기본값이며, 추가 API는 [API 연동 명세](03-api-integration.md)의 변경 목록으로 추적한다. 아직 프론트 구현이나 백엔드 보완이 완료된 상태는 아니다.

## 2. 사용자와 해결할 문제

| 사용자 | 주요 목표 | 제공할 경험 |
| --- | --- | --- |
| 방문자 | 원하는 날·지역의 경기 확인 | 로그인 없이 검색·상세 탐색 |
| 일반 회원 | 참가·취소·일정 확인 | 선착순 확정, 내 경기·알림 |
| 경기 생성자 | 인원 모집·일정 운영 | 자동 참가, 수정·삭제·강퇴 |
| 관리자 | 신고 검토·제재 관리 | 승인/거절과 별도 제재 실행 |

생성자는 별도 계정 권한이 아니라 특정 경기의 소유자다. ADMIN은 현재 서버에서 USER를 자동 상속하지 않는다. 일반 화면에서 관리자가 참가할 수 있다고 가정하지 않는다.

## 3. 제품 원칙

1. 경기 탐색은 날짜·지역·조건과 인원 상태가 빠르게 비교되어야 한다.
2. 참가 요청이 서버에서 성공한 뒤에만 확정으로 표시한다.
3. 버튼의 표시·활성 여부에는 사용자 관계와 시간 제한을 함께 반영한다.
4. 모집 상태와 예정/진행/종료 상태를 별도로 표현한다.
5. 존재하지 않는 기능·데이터를 실제 서비스처럼 표시하지 않는다.
6. 모든 실패 화면에 다음 행동을 제공한다. 예: 정원 초과→상세 새로고침, 인증 만료→재로그인.

## 4. 출시 범위

### 4.1 구현 마일스톤 A: 핵심 사용 흐름

- 공개 경기 목록·상세, 날짜·키워드·시도·형식·성별·실내외·모집 상태 검색, 정렬·페이지.
- 이메일 인증 가입, 이메일 로그인·로그아웃, 만료 토큰 갱신, 비밀번호 재설정.
- 경기 생성·수정·삭제, 참가·취소, 확정 참가자 조회와 생성자의 강퇴.
- 내 경기, 프로필 수정·비밀번호 변경·탈퇴.
- 읽지 않은 알림 조회·읽음 처리.

이 단계는 개발·통합 검증판이다. 신고 처리 수단이 없는 상태로 사용자 신고 기능만 먼저 공개하지 않는다.

### 4.2 구현 마일스톤 B: MVP 출시 완료 범위

- 카카오 로그인·신규 가입 추가 정보 입력.
- 인증된 SSE 구독, 중복 이벤트 처리·재연결·DB 알림 복구.
- 종료 경기의 참가자 신고.
- 관리자 신고 목록·승인/거절·승인 신고 기반 별도 7일 제재·제재 이력.
- 모바일 대응·키보드 접근·실패 복구·배포 검증.

출시 MVP는 A+B다. 인증 저장 정책·OAuth 복귀·내 참가 상태 등 선행 보완은 출시 전 완료 조건에 포함한다.

### 4.3 후속 검토 및 제외 범위

| 항목 | 처리 |
| --- | --- |
| 지도·주소 자동 완성 | 우선 전체 주소 직접 입력. SDK·좌표 연동은 후속 |
| 거리순·시간대 범위 필터 | 현재 서버 계약 없음. 검색 API 확장 후 검토 |
| 알림 총 개수·전체 이력·전체 읽음 | 현재 API 없음. 초기에는 읽지 않은 목록만 |
| 관심 경기·친구·팀·채팅·평가 | MVP 제외 |
| 구장 예약·결제·가격·쿠폰·환불 | MVP 제외 |
| 경기장 사진·사진 업로드·시설 정보 | 현재 데이터 없음. 임의 실사진/시설 배지 표시 제외 |
| 다중 기기 독립 세션·자동 로그인 | 서버 세션 정책 확장 후 검토 |
| 공개 경기 SEO·SSR | 검색 유입 요구가 확인되면 재평가 |

참고 사이트의 소셜/게스트/팀/구장 예약 탭을 그대로 만들지 않는다. 우리 탐색은 `경기 찾기 / 내 경기`를 중심으로 구성한다. 날짜 URL `2026-11-09`는 참고 화면의 예시이며 서비스 기본 날짜로 고정하지 않는다.

## 5. 핵심 사용자 여정

### J-01 경기 탐색과 참가

홈 진입 → 날짜·조건 선택 → 경기 상세 → 로그인 필요 안내 → 가입 또는 로그인 → 원래 상세로 복귀 → 참가 확인 → 서버 확정 응답 → 내 경기 확인.

로그인 복귀 경로는 내부 상대 경로만 허용한다. 재진입 시 경기 모집 여부와 내 참가 상태를 다시 조회한다. 그 사이 정원이 차면 실패를 정상적으로 안내한다.

### J-02 생성자의 경기 운영

로그인 → 경기 만들기 → 장소·정원·일정 입력 → 생성 성공 및 본인 자동 참가 → 상세에서 참가자 확인 → 수정/강퇴/삭제를 각 허용 시간 안에서 실행.

### J-03 계정 복구와 세션 종료

비밀번호 재설정 → 인증번호 요청 → 코드 확인 → 새 비밀번호 입력 → 로그인. API 토큰 만료는 갱신 1회로 복구하고 실패하면 로그인으로 안내한다. 제재 오류는 갱신을 반복하지 않는다.

### J-04 신고와 관리자 처리

종료 경기 → 참가자 선택 → 신고 유형·내용 제출 → 접수 안내 → 관리자가 대기 신고 검토 → 승인 또는 거절 → 승인된 신고에 대해 별도 제재 확인·실행.

## 6. 성공 기준

| ID | 확인할 결과 |
| --- | --- |
| P-01 | 비회원이 날짜·지역 필터를 사용하고 URL 공유/새로고침 후 같은 조건을 확인할 수 있다 |
| P-02 | 회원이 실제 서버에서 참가 확정 후 내 경기에서 확인할 수 있다 |
| P-03 | 생성자·참가자·미참가자의 액션이 구분되고 서버 권한 거부도 처리된다 |
| P-04 | 정원 경쟁·시간 만료·중복 참가가 흰 화면이나 잘못된 확정 표시를 만들지 않는다 |
| P-05 | 로그아웃·계정 전환 뒤 이전 사용자의 데이터와 알림 연결이 남지 않는다 |
| P-06 | 관리자 신고 승인이 자동 제재로 오인되지 않고 별도 결과가 확인된다 |
| P-07 | 390px 모바일과 1440px 데스크톱에서 탐색·폼·주요 액션이 사용 가능하다 |

임의 전환율이나 응답 속도를 실측 성과처럼 기록하지 않는다. 초기 출시 전에는 아래 인수 문서의 시나리오 통과를 기준으로 하고, 실제 사용 데이터가 쌓이면 탐색→상세→참가 전환을 측정한다.
