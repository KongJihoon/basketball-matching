# 영속 알림과 실시간 SSE 알림 리팩터링

## 1. 개요

알림 기능은 알림 내역을 저장하는 책임과 사용자의 현재 연결로 즉시 전달하는 책임을 함께 가진다. 그러나 모든 이벤트가 동일한 전달 보장과 보관 기간을 요구하지는 않는다.

이번 리팩터링에서는 신고·블랙리스트·경기 변경처럼 사용자가 나중에도 확인해야 하는 알림은 DB에 저장하고, 경기 생성처럼 실시간 노출이 중심인 이벤트는 Redis Pub/Sub과 SSE로 전달하도록 구분했다.

---

## 2. 기존 문제

- 메모리의 `SseEmitter`만 사용하면 서버 재시작 후 연결과 미수신 이벤트를 복원할 수 없다.
- 트랜잭션 커밋 전에 알림을 보내면 원본 작업이 롤백돼도 사용자가 성공 알림을 받을 수 있다.
- 서버가 여러 대일 때 한 인스턴스에서 생성한 이벤트를 다른 인스턴스의 SSE 연결에 전달할 수 없다.
- 알림 읽기 API에서 수신자 소유권을 확인하지 않으면 다른 사용자의 알림을 변경할 수 있다.
- 재연결 이벤트 ID가 충돌하거나 순서 비교가 불가능하면 누락 이벤트를 정확히 선택할 수 없다.

---

## 3. 목표와 전달 정책

- 영속 알림은 먼저 DB에 저장한 뒤 SSE로 전달한다.
- 원본 도메인 이벤트는 트랜잭션 커밋 이후 처리한다.
- 경기 생성 실시간 알림은 Redis Pub/Sub을 통해 모든 애플리케이션 인스턴스에 전파한다.
- 사용자는 자신의 읽지 않은 알림만 최신순으로 조회한다.
- 읽음 처리는 수신자 본인에게만 허용하며 멱등성을 보장한다.
- 재연결 시 `Last-Event-ID`보다 새로운 로컬 캐시 이벤트를 순서대로 재전송한다.
- 장기 보존과 반드시 전달되어야 하는 알림은 DB를 원본으로 사용한다.

---

## 4. 최종 구조

```text
NotificationController
  └─ NotificationService
       ├─ NotificationRepository / NotificationQueryRepository
       ├─ UserRepository
       └─ EmitterRepository

도메인 AFTER_COMMIT Listener
  └─ NotificationService.send() → DB 저장 → 로컬 SSE 전송

GameCreatedAfterCommitListener
  └─ Redis topic: game.created
       └─ NotificationRedisSubscriber
            └─ 로컬 EmitterRepository → SSE 전송
```

`NotificationEntity`는 영속 알림과 읽음 상태를 담당한다. `EmitterRepository`는 현재 인스턴스에 연결된 SSE 세션과 짧은 재연결 캐시를 관리한다. Redis는 인스턴스 간 실시간 메시지 전파에 사용되며 영속 저장소 역할을 하지 않는다.

---

## 5. SSE 구독과 재연결

구독 시 활성 사용자를 확인하고 30분 타임아웃의 `SseEmitter`를 만든다. 연결 완료, 타임아웃, 오류 콜백에는 저장된 emitter를 제거해 메모리 누수를 방지한다.

```text
GET /api/v1/notifications/subscribe
 → 사용자 검증
 → userId_emitter_UUID 생성
 → emitter 저장 및 종료 콜백 등록
 → connect 이벤트 전송
 → Last-Event-ID가 있으면 누락 이벤트 재전송
```

이벤트 ID는 사용자 ID, 밀리초 시각, 증가 시퀀스를 고정 길이로 조합한다. 같은 밀리초에 여러 이벤트가 생성되어도 충돌하지 않고 문자열 정렬 순서가 생성 순서를 유지한다.

로컬 이벤트 캐시는 5분 TTL이며 조회나 저장 시 만료 데이터를 정리한다. 따라서 재연결 보장은 같은 인스턴스와 TTL 범위 안에서만 유효하다.

---

## 6. 영속 알림 흐름

`NotificationService.send()`는 다음 순서로 동작한다.

1. `NotificationEntity`를 정적 팩토리 메서드로 생성한다.
2. DB에 저장한다.
3. 응답 객체와 고유 이벤트 ID를 만든다.
4. 재연결을 위해 이벤트를 로컬 캐시에 저장한다.
5. 수신자의 모든 emitter에 전송한다.
6. 전송 중 `IOException`이 발생한 emitter는 제거한다.

경기 수정·삭제·강퇴·블랙리스트 알림은 원본 트랜잭션의 `AFTER_COMMIT` 리스너에서 새 트랜잭션으로 이 메서드를 호출한다. 원본 작업의 확정과 알림 저장 순서를 보장하면서 알림 실패가 원본 결과를 되돌리지 않게 한다.

---

## 7. Redis Pub/Sub 실시간 알림

경기 생성 커밋 후 `GameCreatedAfterCommitListener`가 메시지를 직렬화해 `game.created` 채널로 발행한다. 각 인스턴스의 `NotificationRedisSubscriber`가 메시지를 수신하고 해당 인스턴스에 연결된 사용자에게 SSE로 전달한다.

이 방식은 다중 인스턴스의 로컬 emitter 문제를 해결하지만 Redis Pub/Sub 자체는 메시지를 저장하거나 재전송하지 않는다. 구독자가 순간적으로 연결되지 않았거나 Redis 장애가 발생하면 경기 생성 알림은 유실될 수 있다. 이는 경기 생성 알림을 실시간 편의 정보로 정의한 현재 정책에서 수용한 트레이드오프이다.

향후 반드시 전달해야 하는 요구로 바뀌면 DB 저장, Redis Streams 또는 메시지 브로커를 검토해야 한다.

---

## 8. 목록 조회와 읽음 처리

읽지 않은 알림 목록은 QueryDSL로 수신자와 `isRead=false`를 조건으로 조회한다. 정렬은 `createdAt DESC, notificationId DESC`를 사용해 같은 생성 시각에도 순서를 결정한다.

읽음 처리는 `notificationId`와 `receiverUserId`를 함께 조건으로 조회한다. 단순 ID 조회 후 자바 코드에서 비교하는 대신 저장소 조회 단계에서 소유권을 제한한다.

`markAsRead()`는 이미 읽은 알림이면 바로 반환한다. 반복 요청에도 최초 `readDateTime`을 보존하므로 멱등하다.

---

## 9. 테스트와 운영상 한계

단위 테스트는 다음을 검증한다.

- 읽지 않은 알림 조회와 사용자 미존재
- 자신의 알림 읽기와 타인 알림 접근 차단
- 반복 읽기 시각 보존
- 알림 저장, 이벤트 캐시 및 emitter 전달

통합 테스트는 실제 DB에서 알림 저장, 최신순 조회, 읽음 처리 후 목록 제외, 소유권 조건을 검증한다. SSE 연결과 즉시 전달은 API로 수동 확인했으며 장시간 연결 종료와 자동 재연결은 클라이언트 테스트가 추가로 필요하다.

현재 구조의 한계는 다음과 같다.

- 로컬 재연결 캐시는 인스턴스 이동에 취약하다.
- heartbeat가 없어 중간 네트워크 장비의 유휴 연결 종료를 빠르게 감지하기 어렵다.
- Pub/Sub은 at-most-once 특성이며 실패 재시도가 없다.
- 영속 알림 리스너도 Outbox가 없어 프로세스 종료 시 유실 가능성이 남는다.

---

## 10. 성과

- DB 영속성과 SSE 실시간성을 역할에 맞게 결합했다.
- 커밋 이후 이벤트로 원본 도메인 작업과 알림 처리를 분리했다.
- Redis Pub/Sub으로 다중 인스턴스의 실시간 전달 경로를 마련했다.
- 사용자별 emitter ID와 순서 가능한 이벤트 ID로 연결 격리와 재연결을 지원했다.
- 소유권 조건 조회와 멱등 읽음 처리로 알림 상태의 안전성을 높였다.
- 기능 특성에 따라 전달 보장 수준을 의식적으로 선택하고 남은 운영 한계를 문서화했다.
