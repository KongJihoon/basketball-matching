# 블랙리스트 제재 기능 리팩터링

## 1. 개요

블랙리스트는 신고의 단순 상태값이 아니라 사용자 접근 권한, 진행 예정 경기, 참가 상태, 인증 토큰과 알림에 영향을 주는 독립적인 제재 기능이다.

이번 리팩터링에서는 신고 승인과 제재 적용을 분리하고, 블랙리스트 생성에 반드시 승인된 신고 한 건을 근거로 사용하도록 구성했다. 제재 자체와 경기 정리는 하나의 트랜잭션으로 처리하고, 외부 후속 작업은 커밋 이후 이벤트로 분리했다.

---

## 2. 기존 문제

신고 건수만으로 자동 제재하면 사실관계가 확인되지 않은 신고도 사용자 이용 제한으로 이어질 수 있다. 또한 블랙리스트 저장, 경기 취소, 참가 취소, 토큰 제거, 알림 전송을 한 메서드에서 모두 처리하면 다음 문제가 생긴다.

- 하나의 외부 작업 실패가 핵심 제재 트랜잭션까지 롤백시킨다.
- 서비스 책임과 트랜잭션 경계가 불명확해진다.
- 만료 상태를 별도 컬럼으로 저장하면 시간 경과에 따라 실제 상태와 DB 값이 어긋날 수 있다.
- 같은 신고를 여러 제재에 재사용하거나 한 사용자에게 활성 제재를 중복 부여할 수 있다.

---

## 3. 리팩터링 목표와 정책

- 관리자만 제재를 생성하고 조회한다.
- `APPROVED` 신고만 제재 근거로 사용할 수 있다.
- 신고 한 건은 블랙리스트 한 건에만 사용한다.
- 이미 활성 제재 중인 사용자는 다시 제재하지 않는다.
- 기본 제재 기간은 7일이다.
- 제재 시작 시각보다 종료 시각이 반드시 늦어야 한다.
- 제재 대상의 예정 경기 및 참가 관계를 즉시 정리한다.
- Refresh Token 제거와 알림은 핵심 트랜잭션 커밋 후 처리한다.
- 신고 승인과 블랙리스트 생성은 별개의 관리자 판단으로 유지한다.

---

## 4. 최종 구조와 책임

```text
BlackListController
  └─ BlackListService
       ├─ UserRepository
       ├─ ReportRepository
       ├─ BlackListRepository
       ├─ BlackListGameService
       └─ ApplicationEventPublisher

UserBlacklistedEvent
  └─ UserBlacklistedEventListener(AFTER_COMMIT, REQUIRES_NEW)
       ├─ AuthTokenStore
       └─ NotificationService
```

`BlackListService`는 제재 가능 여부와 저장을 담당한다. `BlackListGameService`는 같은 트랜잭션에서 경기 도메인의 정합성을 정리한다. 이벤트 리스너는 커밋 이후 토큰과 알림이라는 후속 효과를 수행한다.

---

## 5. 제재 생성 흐름

```text
관리자 요청
 → 활성 관리자 조회
 → 신고 조회
 → 신고 APPROVED 검증
 → 해당 신고의 기존 제재 사용 여부 검증
 → 대상 사용자의 활성 제재 검증
 → bannedAt / expiresAt(+7일) 계산
 → BlackListEntity 생성 및 저장
 → 예정 경기와 참가 관계 정리
 → UserBlacklistedEvent 발행
 → 트랜잭션 커밋
 → Refresh Token 제거 및 알림 전송
```

검증 순서는 오류 의미와 불필요한 작업을 고려한다. 승인되지 않은 신고는 먼저 차단하고, 이미 사용된 신고와 활성 제재를 확인한 뒤에만 엔티티를 생성한다.

DB의 신고 연관관계에는 유일 제약조건 `uq_black_list_report`를 두어 애플리케이션 검증을 우회하는 동시 요청에도 같은 신고의 재사용을 최종 방어한다.

---

## 6. 경기 도메인 정리와 트랜잭션

`BlackListGameService.cleanup()`은 `Propagation.MANDATORY`를 사용한다. 따라서 독립적으로 실행될 수 없고 반드시 블랙리스트 생성 트랜잭션 안에서 호출된다.

정리 대상은 다음 두 종류이다.

1. 제재 대상이 생성한 미래 경기
   - 참가 관계를 정리한다.
   - 경기를 취소한다.
   - 다른 참가자에게 전달할 경기 취소 알림 정보를 수집한다.
2. 제재 대상이 참가한 다른 미래 경기
   - 참가 상태와 인원수를 정책에 맞게 정리한다.

블랙리스트 저장만 성공하고 경기 정리가 실패하면 데이터가 모순되므로 이 둘은 원자적으로 성공하거나 함께 롤백되어야 한다. 반면 알림 실패는 이미 확정된 제재를 되돌릴 이유가 없으므로 커밋 이후로 분리한다.

---

## 7. 만료 상태와 접근 차단

블랙리스트 엔티티에는 갱신이 필요한 상태 컬럼을 두지 않는다. 조회 시각을 기준으로 상태를 계산한다.

```text
expiresAt > now  → ACTIVE
expiresAt <= now → EXPIRED
```

따라서 만료 시각이 지나면 스케줄러가 `EXPIRED`로 변경하지 않아도 즉시 비활성으로 판정된다. DB 행은 제재 이력으로 남지만 로그인과 요청 검증에서는 `expiresAt > now`인 행만 차단한다.

현재 `BlackListStore`는 Redis가 아니라 DB의 활성 블랙리스트 존재 여부를 조회한다. 다음 영역에서 이 검증을 사용한다.

- 로그인 시 인증 허용 여부
- 인증 필터에서 보호 API 요청 허용 여부
- 경기 참가 처리 시 참가 가능 여부

향후 Redis 캐시를 도입한다면 TTL을 `expiresAt - now`로 설정해 자연 만료시키는 방법을 검토할 수 있다. 다만 DB를 제재 이력의 원본으로 유지하고 캐시 불일치와 장애 시 대체 전략을 먼저 정해야 한다.

---

## 8. 커밋 이후 이벤트 처리

`UserBlacklistedEventListener`는 `AFTER_COMMIT`에 실행되며 각 후속 작업을 `REQUIRES_NEW` 트랜잭션에서 처리한다.

- 대상 사용자의 Refresh Token 제거
- 대상 사용자에게 제재 알림 저장 및 전송
- 취소된 경기에 참가하던 사용자에게 알림 저장 및 전송

활성 Access Token은 Refresh Token 삭제만으로 즉시 무효화되지 않는다. 대신 매 요청의 인증 필터에서 활성 블랙리스트를 검사해 접근을 차단한다.

리스너는 후속 처리 예외를 기록하고 핵심 제재 결과에는 영향을 주지 않는다. 이 구조는 가용성을 높이지만 프로세스 종료나 일시 장애 시 이벤트를 잃을 수 있다. 높은 전달 보장이 필요하다면 Outbox, 재시도, 실패 이벤트 저장을 추가해야 한다.

---

## 9. 테스트 전략과 남은 과제

단위 테스트에서는 다음 정책을 격리해 검증한다.

- 승인된 신고를 근거로 한 생성 성공과 이벤트 내용
- 미승인 신고 거절
- 같은 신고 재사용 거절
- 활성 제재 중복 거절
- 현재 시각에 따른 `ACTIVE`, `EXPIRED` 분류

통합 테스트에서는 실제 DB 제약조건과 트랜잭션 후속 효과를 확인한다.

- 블랙리스트 및 신고 연관관계 저장
- 활성 목록과 만료 목록 분리
- 만료 후 `BlackListStore`가 차단하지 않는지 검증
- 실제 커밋 후 Refresh Token 삭제
- 대상 경기 취소와 알림 저장

남은 과제는 이벤트 유실 방지, 다중 관리자 동시 제재 처리, Redis 캐시 도입 시 정합성 정책, 관리자의 제재 해제 및 기간 변경 감사 로그이다.

---

## 10. 성과

- 신고 승인과 서비스 제재를 분리해 관리자 판단 단계를 명확히 했다.
- 승인 신고와 활성 제재를 이중 검증해 중복 제재를 방지했다.
- 제재와 경기 정리를 하나의 트랜잭션으로 묶어 도메인 정합성을 보호했다.
- 토큰 제거와 알림을 커밋 이후로 분리해 핵심 트랜잭션의 책임을 줄였다.
- 상태 컬럼 갱신 없이 시간 비교로 만료를 자동 반영했다.
- 단위·통합·이벤트 통합 테스트로 정책, DB 제약조건, 커밋 이후 효과를 단계별로 검증했다.
