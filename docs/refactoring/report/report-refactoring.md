# 신고 접수와 관리자 검토 기능 리팩터링

## 1. 개요

신고 기능은 단순히 사용자 두 명의 ID와 사유를 저장하는 기능이 아니다. 실제 경기에 참가한 사용자인지, 신고할 수 있는 기간인지, 같은 관계를 중복 신고하는지, 관리자가 이미 처리한 신고인지를 함께 검증해야 한다.

기존 구조는 신고를 접수한 즉시 신고 횟수를 기준으로 제재를 적용하는 흐름이 섞일 수 있었고, 신고 자격과 관리자 판단의 경계도 명확하지 않았다.

이번 리팩터링은 다음 세 가지를 분리하는 데 중점을 두었다.

- 참가자의 신고 접수
- 관리자의 신고 사실 판단
- 승인된 신고를 근거로 한 별도의 제재

신고는 사건 기록이고, 승인은 관리자의 판단이며, 블랙리스트는 서비스 이용을 제한하는 제재이다. 이 세 개념을 하나의 상태로 다루지 않는 것이 핵심이다.

---

## 2. 기존 문제

### 신고 자격이 불명확한 문제

임의의 사용자 ID만 알면 신고할 수 있다면 다음 문제가 발생한다.

- 경기에 참가하지 않은 사용자가 신고할 수 있다.
- 경기에 참가하지 않은 사용자를 신고할 수 있다.
- 진행 중인 경기나 수개월 전의 경기를 근거로 신고할 수 있다.
- 자기 자신을 신고하는 잘못된 요청을 막지 못한다.

### 신고와 제재의 결합

신고 건수만으로 자동 제재하면 허위 신고나 집단 신고가 바로 서비스 이용 제한으로 이어질 수 있다. 또한 신고 승인 이유와 제재 실행 주체를 별도로 추적하기 어렵다.

### 중복 신고 기준의 불명확성

같은 대상을 누군가 이미 신고했다는 이유로 모든 추가 신고를 막으면, 여러 참가자가 동일한 피해를 겪은 사실을 기록하지 못한다. 반대로 아무 기준 없이 허용하면 한 사용자가 같은 경기와 대상을 계속 신고할 수 있다.

---

## 3. 리팩터링 목표와 최종 정책

신고 접수 정책을 다음과 같이 확정했다.

1. 종료된 경기만 신고할 수 있다.
2. 경기 종료 후 7일 이내에만 신고할 수 있다.
3. 해당 경기의 `ACCEPT` 참가자만 신고할 수 있다.
4. 해당 경기의 다른 `ACCEPT` 참가자만 신고할 수 있다.
5. 자기 자신은 신고할 수 없다.
6. 중복 기준은 `경기 + 신고자 + 신고 대상`이다.
7. 서로 다른 사용자가 같은 대상을 신고하는 것은 허용한다.
8. 신고 유형은 비매너, 노쇼, 욕설·언어폭력 세 가지를 사용한다.
9. 신고 내용은 필수이며 최대 500자다.
10. 관리자는 신고를 승인하거나 거절한다.
11. 신고 승인과 블랙리스트 제재는 별도 행위로 다룬다.
12. 신고 건수만으로 자동 제재하지 않는다.

이 정책으로 신고 기록의 신뢰성과 관리자 판단의 추적 가능성을 함께 확보했다.

## 4. 적용한 구조와 API 책임

패키지는 기술 구현이 아니라 신고 도메인을 기준으로 구성했다.

```text
report
├── controller
│   ├── ReportController
│   └── AdminReportController
├── domain
│   └── ReportEntity
├── dto
│   ├── request
│   │   ├── CreateReportRequest
│   │   └── ReviewReportRequest
│   └── response
│       ├── CreateReportResponse
│       ├── ReportListResponse
│       └── ReviewReportResponse
├── repository
│   └── ReportRepository
├── service
│   └── ReportService
└── type
    ├── ReportType
    ├── ReportStatus
    └── ReportDecision
```

일반 사용자 API와 관리자 API를 분리했다.

```text
POST  /api/v1/games/{gameId}/reports
GET   /api/v1/admin/reports?status=PENDING&page=0&size=20
PATCH /api/v1/admin/reports/{reportId}
```

`ReportController`는 경기 리소스 아래에 신고를 생성하고 `201 Created`와 `Location` 헤더를 반환한다. `AdminReportController`는 클래스 단위 `hasRole('ADMIN')`으로 관리자 권한을 제한한다.

## 5. 신고 접수 흐름과 검증 순서

`ReportService.createReport()`는 다음 순서로 진행된다.

```text
자기 신고 검증
→ 활성 경기 조회
→ Clock으로 신고 시각 생성
→ 경기 종료 및 7일 기간 검증
→ 활성 신고자 조회
→ 신고자의 ACCEPT 참가 검증
→ 신고 대상의 ACCEPT 참가 검증
→ 신고 대상 조회
→ 중복 신고 검증
→ PENDING 신고 생성 및 저장
```

자기 신고를 먼저 검증하면 DB 조회 없이 명백히 잘못된 요청을 즉시 차단할 수 있다. 이후 경기 시간과 참가 관계를 확인해 신고 자격을 증명한다.

경기 종료 정확히 7일 후의 시각은 허용하고, 그보다 늦은 시각은 차단한다. 코드가 `reportedAt.isAfter(gameEndedAt.plusDays(7))`를 사용하기 때문이다.

신고 대상은 `findById()`로 조회한다. 이는 경기 당시에 확정 참가했던 사용자의 역사적 관계를 신고 근거로 남길 수 있는 현재 구현을 반영한다. 탈퇴 사용자 신고 허용 여부는 운영 정책으로 추가 검토할 수 있다.

## 6. 신고 상태와 관리자 검토

신고 상태는 다음 세 가지다.

```text
PENDING  : 접수되었지만 관리자가 판단하지 않음
APPROVED : 신고 내용이 유효하다고 판단
REJECTED : 제공된 정보만으로 인정하기 어렵거나 유효하지 않음
```

허용되는 상태 전이는 다음뿐이다.

```text
PENDING → APPROVED
PENDING → REJECTED
```

`ReportEntity.approve()`와 `reject()`는 먼저 `validatePending()`을 호출한다. 이미 처리된 신고를 다시 승인하거나 거절하면 `REPORT_ALREADY_PROCESSED`가 발생한다.

관리자 검토 시 다음 값을 함께 저장한다.

- 최종 상태
- 검토한 관리자
- 검토 사유
- 검토 시각

이 정보는 추후 민원, 제재 근거 확인, 관리자 감사 로그의 기초가 된다.

## 7. 데이터 정합성과 트랜잭션

중복 신고는 서비스 사전 조회와 DB 유일 제약조건을 함께 사용한다.

```text
uq_report_reporter_target_game
(report_user_id, target_user_id, game_entity_game_id)
```

서비스 검증은 사용자에게 의미 있는 `ALREADY_REPORTED_USER` 예외를 제공한다. DB 유일 제약조건은 동시 요청이 서비스의 `exists` 검증을 함께 통과하는 경우에도 최종 정합성을 보호한다.

신고 생성과 검토는 각각 하나의 DB 트랜잭션으로 실행된다. 검토 메서드는 엔티티 상태를 변경하고 JPA Dirty Checking으로 반영한다.

신고 목록은 상태를 조건으로 최신 접수 순으로 페이징한다. `ReportListResponse.fromEntity()`가 경기, 신고자, 대상자 정보에 접근하므로 신고 목록의 쿼리 수와 N+1 가능성은 성능 개선 단계에서 실제 측정할 후속 과제다.

## 8. 테스트 전략

### 단위 테스트

`ReportServiceUnitTest`는 Mockito와 `Clock.fixed()`를 사용해 정책 분기를 검증한다.

- 종료된 경기의 확정 참가자 신고 성공
- 자기 신고 차단
- 미종료 경기 차단
- 종료 후 7일이 지난 신고 차단
- 신고자가 확정 참가자가 아닌 경우 차단
- 신고 대상이 확정 참가자가 아닌 경우 차단
- 같은 경기·신고자·대상 중복 차단
- 승인과 거절 상태 전이

### 통합 테스트

`ReportServiceIntegrationTest`는 Testcontainers MySQL을 사용한다.

- 신고 엔티티와 연관관계 저장
- 중복 신고 차단
- 서로 다른 참가자의 동일 대상 신고 허용
- 상태별 관리자 목록 조회
- 승인 시 검토 정보 Dirty Checking

단위 테스트는 정책 분기와 호출 순서를 빠르게 검증하고, 통합 테스트는 유일 제약조건·JPA·실제 MySQL의 동작을 검증한다.

## 9. 트레이드오프와 남은 과제

### 현재 선택의 장점

- 신고 건수와 무관하게 관리자가 각 사건을 판단한다.
- 신고 기록과 서비스 제재 기록을 별도로 추적할 수 있다.
- 참가 관계와 시간을 검증해 허위 신고 범위를 줄였다.
- 상태 전이 방법을 엔티티에 두어 우회를 막았다.

### 남은 과제

- 신고 증거 파일이나 이미지 첨부 정책
- 신고 취소 또는 내 신고 조회 정책
- 관리자 검토 권한의 세분화와 감사 로그
- 동시 관리자 검토에 대한 낙관적 락 또는 조건부 UPDATE 검토
- 관리자 목록 조회 N+1 실측정 및 Fetch Join/Projection 검토
- 복수 신고를 하나의 사건으로 그룹화하는 운영 모델

---

## 10. 성과

- 신고 가능 대상과 기간을 명확한 도메인 정책으로 정리했다.
- 확정 참가 정보를 이용해 신고자와 대상의 자격을 검증했다.
- 신고 접수, 관리자 판단, 서비스 제재를 분리했다.
- `PENDING → APPROVED/REJECTED` 상태 전이를 엔티티가 보호하도록 변경했다.
- 서비스 검증과 DB 유일 제약조건을 결합해 중복 신고를 방지했다.
- 관리자·상태·사유·시각을 함께 저장해 판단 과정을 추적할 수 있게 했다.
- 고정 `Clock`과 Testcontainers MySQL을 사용해 시간 정책과 DB 정합성을 반복 가능하게 검증했다.
