# 블랙리스트 만료와 트랜잭션 이벤트 학습 정리

## 1. 블랙리스트의 역할

블랙리스트는 단순 표시가 아니라 인증과 도메인 행위를 제한하는 정책이다. 현재 프로젝트에서는 로그인, 인증된 API 요청, 경기 참가에서 활성 블랙리스트를 확인한다.

제재가 생성되면 대상 사용자가 만든 미래 경기와 다른 경기의 참가 관계도 정리한다. 따라서 블랙리스트는 인증 도메인만의 기능이 아니라 사용자, 신고, 경기, 인증, 알림을 연결하는 유스케이스다.

---

## 2. 승인 신고와 제재 불변식

제재 엔티티 생성에는 다음 조건이 필요하다.

- 신고 상태가 `APPROVED`이다.
- 제재 종료 시각이 시작 시각보다 늦다.
- 제재 대상은 신고의 대상 사용자와 동일하다.

첫 번째와 두 번째는 `BlackListEntity.create()`가 검증하고 대상 사용자는 외부 입력이 아니라 `report.getTargetUser()`에서 결정한다. 외부가 target ID를 별도로 전달하면 신고 대상과 다른 사용자에게 제재할 가능성이 생기기 때문이다.

같은 신고 재사용과 기존 활성 제재 여부처럼 저장소 조회가 필요한 규칙은 서비스가 검증한다.

---

## 3. 저장 상태와 계산 상태

상태를 저장하는 방식은 만료 시점마다 갱신 작업이 필요하다.

```text
DB status = ACTIVE
시간 경과
실제 의미 = EXPIRED
DB status = ACTIVE  ← 스케줄러 실행 전 불일치
```

현재 구현은 `bannedDateTime`과 `expiresAt`만 저장하고 상태를 계산한다.

```java
public boolean isActive(LocalDateTime now) {
    return expiresAt.isAfter(now);
}
```

이 모델에서는 만료 처리 배치가 없어도 경계를 지난 즉시 비활성이다. 정확히 `expiresAt`인 순간에는 `isAfter(now)`가 거짓이므로 `EXPIRED`이다.

계산 상태가 적합한 경우는 상태가 오직 시간으로만 결정되고 만료 시 별도 업무 처리가 필요하지 않을 때다. 만료 알림, 복구 작업, 통계 확정 등이 필요하면 스케줄러나 이벤트 처리가 별도로 필요할 수 있다.

---

## 4. 활성 차단과 토큰 관계

Refresh Token을 삭제해도 이미 발급된 Access Token은 자체 만료 전까지 암호학적으로 유효하다. 즉 토큰 삭제만으로 즉시 로그아웃이 완성되지는 않는다.

현재는 인증 필터가 매 요청마다 활성 블랙리스트를 조회해 Access Token이 남아 있어도 요청을 차단한다. 로그인 시에도 같은 검증을 수행해 새 토큰 발급을 막는다.

이 방식은 즉시성이 높지만 요청마다 DB 조회 비용이 발생한다. 향후 병목이 확인되면 활성 여부를 Redis에 캐시할 수 있다. 이때 TTL은 남은 제재 기간으로 설정할 수 있지만 다음을 정해야 한다.

- DB 저장 성공과 캐시 기록 실패 시 처리
- 제재 조기 해제 시 캐시 삭제
- Redis 장애 시 fail-open 또는 fail-closed
- 캐시가 없을 때 DB 조회 후 채우는 방식

현재 구현은 DB 조회이며 캐시 도입은 계획이지 완료된 기능이 아니다.

---

## 5. 트랜잭션 경계 결정

블랙리스트 저장과 예정 경기 정리는 서로 다른 결과가 되면 안 된다.

```text
블랙리스트 저장 성공 + 경기 정리 실패 → 제재됐지만 모집 경기는 유지
블랙리스트 저장 실패 + 경기 정리 성공 → 제재 없이 경기만 취소
```

따라서 두 작업은 같은 트랜잭션으로 묶는다. `BlackListGameService.cleanup()`의 `MANDATORY`는 현재 트랜잭션이 없으면 예외를 발생시켜 잘못된 독립 호출을 방지한다.

트랜잭션은 무조건 크게 묶는 것이 좋다는 뜻이 아니다. 데이터 정합성을 위해 함께 성공해야 하는 DB 작업을 묶고, 실패해도 핵심 상태를 되돌릴 필요가 없는 외부 부수 효과는 분리한다.

---

## 6. `AFTER_COMMIT`과 `REQUIRES_NEW`

이벤트를 일반 `@EventListener`로 처리하면 발행 시점에 즉시 실행돼 원본 트랜잭션이 아직 커밋되지 않았을 수 있다. `@TransactionalEventListener(phase = AFTER_COMMIT)`은 원본 트랜잭션이 성공적으로 커밋된 후 리스너를 호출한다.

커밋 이후에는 원본 트랜잭션의 변경 작업을 계속 수행할 수 없으므로 영속 알림 저장에는 새로운 트랜잭션이 필요하다. 이때 `REQUIRES_NEW`를 사용한다.

```text
원본 TX
  블랙리스트 저장
  경기 정리
  이벤트 발행
COMMIT

후속 TX
  Refresh Token 삭제
  알림 저장 및 전송
```

원본 트랜잭션이 롤백되면 `AFTER_COMMIT` 리스너는 실행되지 않으므로 존재하지 않는 제재에 대한 알림을 방지한다.

---

## 7. 트랜잭션 이벤트의 한계

커밋 이후 이벤트가 메시지 큐와 같은 내구성을 제공하는 것은 아니다. 이벤트 정보는 애플리케이션 프로세스 안에 있다.

```text
DB COMMIT 성공
 → 리스너 실행 직전 서버 종료
 → 후속 작업 유실 가능
```

현재는 후속 실패를 로그로 남기고 핵심 제재를 유지한다. 프로젝트 요구 수준에서는 적절하지만 반드시 전달해야 한다면 Transactional Outbox가 후보가 된다.

Outbox 방식은 핵심 변경과 이벤트 행을 같은 DB 트랜잭션으로 저장하고 별도 워커가 미처리 이벤트를 재시도한다. 전달 신뢰도는 높아지지만 테이블, 폴링/CDC, 멱등성, 운영 모니터링 비용이 생긴다.

---

## 8. 동시성과 DB 제약조건

활성 블랙리스트 존재 여부를 조회한 뒤 저장하는 사이에는 동시성 간격이 있다. 같은 신고는 `report_id` 유일 제약조건으로 중복 사용을 막는다.

그러나 “사용자당 활성 제재 하나”는 만료 시각 조건이 포함돼 일반 유일 인덱스로 바로 표현하기 어렵다. 동시 관리자 요청이 실제로 발생한다면 다음 방식을 비교할 수 있다.

- 신고 행 또는 사용자 행 비관적 락
- 버전 컬럼 기반 낙관적 락
- 별도 활성 제재 키 테이블
- 조건부 INSERT와 제약조건 재설계

락을 먼저 추가하기보다 경쟁 상황을 테스트로 재현하고 실패 형태를 측정한 뒤 선택한다.

---

## 9. 테스트에서 확인할 것

단위 테스트는 서비스 검증과 이벤트 데이터가 핵심이다.

- 미승인 신고가 차단되는가?
- 사용된 신고와 활성 중복이 차단되는가?
- 7일 종료 시각이 정확히 계산되는가?
- 이벤트에 대상, 제재 기간, 경기 취소 알림 정보가 포함되는가?

통합 테스트는 시간 기반 쿼리와 트랜잭션 효과를 확인한다.

- 만료 전 `BlackListStore`가 `true`인가?
- 정확한 만료 시각 이후 `false`인가?
- 상태 컬럼 갱신 없이 목록에서 `EXPIRED`로 보이는가?
- 커밋 후 Refresh Token이 실제 삭제되는가?
- 경기 취소와 알림이 실제 DB에 남는가?

시간 테스트에는 고정 `Clock`을 사용하고, 커밋 이후 리스너 테스트는 테스트 트랜잭션이 끝나는 시점을 의식해야 한다.

---

## 10. 면접 답변 요약

### 만료 배치가 없는데 어떻게 해제되나요?

상태를 저장하지 않고 `expiresAt > now` 조건으로 활성 여부를 계산하므로 만료 순간부터 조회와 인증 검증에서 자동 제외된다.

### 왜 경기 정리는 같은 트랜잭션인가요?

제재 상태와 예정 경기 상태가 서로 모순되면 안 되는 핵심 DB 정합성 작업이기 때문이다.

### 왜 토큰 삭제와 알림은 커밋 이후인가요?

확정되지 않은 제재의 부수 효과를 방지하고 외부 작업 실패가 핵심 트랜잭션을 롤백시키지 않게 하기 위해서다.

### `AFTER_COMMIT`이면 메시지가 반드시 전달되나요?

아니다. 프로세스 종료 구간에서 유실될 수 있다. 강한 전달 보장이 필요하면 Outbox와 멱등 재처리를 도입해야 한다.

### Redis 캐시를 적용한다면 무엇을 주의해야 하나요?

남은 제재 시간을 TTL로 사용할 수 있지만 DB 원본과의 정합성, 조기 해제, Redis 장애 정책을 먼저 설계해야 한다.
