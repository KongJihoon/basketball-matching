# SSE와 Redis Pub/Sub 알림 학습 정리

## 1. Polling, WebSocket, SSE 비교

### Polling

클라이언트가 일정 간격으로 새 알림을 조회한다. 구현과 장애 대응이 단순하지만 새 데이터가 없어도 요청이 반복되고 즉시성은 주기에 의존한다.

### WebSocket

하나의 연결로 서버와 클라이언트가 양방향 통신한다. 채팅처럼 클라이언트도 실시간 메시지를 계속 보내야 할 때 적합하지만 연결 프로토콜과 세션 관리가 더 복잡하다.

### Server-Sent Events

HTTP 연결을 유지하고 서버가 클라이언트 방향으로 이벤트를 전송한다. 알림처럼 서버→클라이언트 단방향 요구에 적합하며 브라우저 `EventSource`는 재연결과 `Last-Event-ID`를 지원한다.

현재 프로젝트는 알림 수신만 실시간이면 되므로 SSE를 선택했다. 사용자의 알림 읽기 같은 클라이언트 행위는 일반 HTTP API로 처리한다.

---

## 2. SSE 프로토콜의 핵심

응답 Content-Type은 `text/event-stream`이며 각 이벤트는 빈 줄로 구분된다.

```text
id:1_event_1787920738947_00000000000000000001
event:notification
data:{"title":"경기 알림","message":"..."}

```

- `id`: 재연결 시 마지막으로 받은 이벤트를 식별한다.
- `event`: 클라이언트가 구분할 이벤트 종류이다.
- `data`: 실제 데이터이며 여러 줄일 수 있다.
- `retry`: 서버가 재연결 권장 시간을 전달할 수 있다.

SSE 연결은 장시간 열려 있으므로 서버, 프록시, 로드밸런서 타임아웃을 함께 고려해야 한다. 현재 emitter 타임아웃은 30분이고 만료 후 클라이언트가 재연결해야 한다.

---

## 3. `SseEmitter` 생명주기

Spring MVC의 `SseEmitter`는 비동기 응답을 유지하고 서버가 이후 데이터를 보낼 수 있게 한다.

연결마다 다음 콜백이 필요하다.

- `onCompletion`: 정상 종료 후 저장소 제거
- `onTimeout`: 제한 시간 초과 후 제거
- `onError`: 연결 오류 후 제거

제거하지 않으면 끊어진 emitter가 메모리에 남고 매 알림마다 실패 전송을 반복한다. 전송 중 `IOException`이 발생한 emitter도 즉시 제거해야 한다.

구독 직후 작은 `connect` 이벤트를 보내는 이유는 연결이 실제로 수립됐음을 확인하고 응답 헤더를 즉시 flush하기 위해서다.

---

## 4. 사용자 격리와 이벤트 ID

문자열 prefix 검색을 사용할 때 사용자 `1`과 `10`이 섞이면 안 된다. 구분자를 포함해 ID를 만든다.

```text
1_emitter_UUID
10_emitter_UUID
```

이벤트 ID는 같은 밀리초에도 여러 개가 생성될 수 있으므로 timestamp만 사용하면 충돌한다. 현재는 `AtomicLong` 시퀀스를 추가하고 고정 길이로 포맷한다.

```text
{userId}_event_{13자리 timestamp}_{20자리 sequence}
```

고정 길이 숫자는 문자열 사전순과 시간·시퀀스 순서를 일치시킨다. 재연결에서는 `Last-Event-ID`보다 큰 키만 정렬해 전송할 수 있다.

`AtomicLong`은 한 프로세스 안의 충돌만 막는다. 다중 인스턴스 전체에서 유일한 ID가 필요하다면 UUID, Redis sequence, ULID 등을 검토해야 한다.

---

## 5. 재연결과 로컬 이벤트 캐시

네트워크가 잠시 끊기면 클라이언트는 마지막으로 처리한 ID를 보내고 서버는 이후 이벤트를 재전송한다. 현재 `EmitterRepository`는 이벤트를 메모리에 5분간 저장한다.

장점은 별도 저장소 없이 짧은 연결 끊김을 보완한다는 것이다. 한계도 명확하다.

- 서버 재시작 시 캐시가 사라진다.
- 로드밸런서가 다른 인스턴스로 연결하면 이전 캐시를 찾지 못한다.
- 5분보다 긴 단절은 복구하지 못한다.

영속 알림은 DB의 읽지 않은 목록 API로 보완할 수 있다. 실시간 전용 경기 생성 알림은 이 범위 밖에서 유실될 수 있으며 현재 정책이 이를 허용한다.

---

## 6. Redis Pub/Sub이 필요한 이유

애플리케이션 서버가 두 대라면 emitter는 각 서버 메모리에 나뉜다.

```text
사용자 A ─ SSE → 서버 1
경기 생성 요청 → 서버 2
```

서버 2가 자신의 emitter만 조회하면 사용자 A에게 알림을 보낼 수 없다. 서버 2가 Redis 채널에 발행하면 서버 1과 서버 2의 구독자가 모두 메시지를 받고 각자의 로컬 연결로 전송할 수 있다.

Redis는 여기서 emitter를 저장하지 않고 인스턴스 사이 이벤트 팬아웃만 담당한다. 연결 객체는 프로세스 자원이므로 Redis에 직렬화해 공유할 수 없다.

---

## 7. Pub/Sub의 전달 보장

Redis Pub/Sub은 메시지를 영속 저장하지 않는다. 발행 시점에 구독 중인 소비자에게만 전달하며 ACK, 재시도, 소비자별 offset이 없다.

따라서 다음 상황에서 유실될 수 있다.

- 구독 애플리케이션이 재시작 중이다.
- Redis 연결이 잠시 끊겼다.
- 메시지를 수신한 직후 애플리케이션이 종료됐다.

이 특성은 일반적으로 at-most-once 전달로 설명한다. 유실을 허용할 수 없는 알림에는 다음 대안이 있다.

- DB 알림 테이블을 원본으로 사용
- Redis Streams의 consumer group과 pending 재처리
- Kafka/RabbitMQ 같은 메시지 브로커
- Transactional Outbox로 DB 커밋과 이벤트 기록을 원자화

기술 선택은 “실시간인가”뿐 아니라 유실, 중복, 순서, 재처리 요구를 기준으로 해야 한다.

---

## 8. 영속 알림과 읽음 상태

중요 알림은 DB에 먼저 저장하고 SSE는 빠른 전달 채널로 사용한다. 연결이 없더라도 사용자는 나중에 읽지 않은 목록을 조회할 수 있다.

읽음 API는 알림 ID만으로 조회하면 안 된다. `notificationId + receiverUserId`를 조건으로 사용해 소유권을 저장소 단계에서 제한한다.

읽음 처리는 반복 요청에도 결과가 같아야 한다.

```java
if (isRead) {
    return;
}
isRead = true;
readDateTime = now;
```

이렇게 하면 네트워크 재시도로 동일 PATCH가 반복돼도 최초 읽은 시각이 바뀌지 않는다. 이를 멱등성이라고 한다.

목록 정렬은 `createdAt DESC`만으로 충분하지 않을 수 있다. 같은 시각의 행 순서가 불안정하므로 PK를 보조 정렬 조건으로 사용한다.

## 9. 운영과 테스트 관점

### 테스트

- 서비스 단위 테스트: 저장, 읽음, 소유권, emitter/cache 호출
- DB 통합 테스트: 영속화, 정렬, 읽음 목록 제외
- SSE 테스트: connect 이벤트, 실시간 이벤트 형식, 재연결 ID
- Redis 통합 테스트: 발행한 메시지가 구독자를 거쳐 로컬 전송으로 이어지는지
- 장애 테스트: 연결 종료, Redis 중단, 서버 재시작 시 기대 동작

### 운영 지표

- 현재 SSE 연결 수와 사용자당 연결 수
- 전송 성공/실패 및 제거된 emitter 수
- 연결 유지 시간과 재연결 빈도
- Redis publish/subscribe 오류
- 알림 이벤트 생성부터 클라이언트 전달까지 지연
- DB 읽지 않은 알림 조회 응답 시간

heartbeat 이벤트를 주기적으로 보내면 죽은 연결을 빨리 발견하고 프록시의 유휴 타임아웃을 방지할 수 있지만, 연결 수만큼 주기적 트래픽이 생긴다.

## 10. 면접 질문과 답변 포인트

### WebSocket 대신 SSE를 선택한 이유는 무엇인가요?

알림은 서버에서 클라이언트로 전달하는 단방향 요구가 중심이고, 클라이언트 행위는 REST API로 충분해 더 단순한 SSE를 선택했다.

### Redis가 있는데 왜 emitter를 로컬에 저장하나요?

`SseEmitter`는 현재 서버의 HTTP 연결 객체라 다른 프로세스에 직렬화해 공유할 수 없다. Redis는 이벤트를 모든 인스턴스로 전파하고 각 인스턴스가 자신의 연결로 보낸다.

### Pub/Sub이면 알림이 보장되나요?

아니다. 구독 중인 소비자에게만 전달되는 at-most-once 방식이다. 중요한 알림은 DB에 저장하고, 더 강한 이벤트 전달에는 Streams나 메시지 브로커, Outbox가 필요하다.

### 재연결은 완전하게 지원하나요?

현재는 같은 인스턴스의 5분 로컬 캐시 범위에서 지원한다. 인스턴스 이동과 서버 재시작까지 보장하려면 공유 이벤트 저장소나 영속 알림 조회가 필요하다.

### 알림을 DB에 저장한 뒤 SSE를 보내는 이유는 무엇인가요?

실시간 연결 실패와 관계없이 사용자가 나중에 알림을 확인할 수 있게 DB를 원본으로 만들기 위해서다.

### 알림 중복은 어떻게 다뤄야 하나요?

재시도 가능한 구조에서는 이벤트 고유 ID와 소비 측 멱등 처리가 필요하다. 현재 Pub/Sub 경로는 재시도가 없고, 읽음 처리는 멱등하게 구현되어 있다.
