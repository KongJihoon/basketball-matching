# 신고 정책과 상태 전이 학습 정리

## 1. 신고 기능이 단순 CRUD가 아닌 이유

신고 생성은 행 하나를 저장하는 작업처럼 보이지만 실제로는 여러 도메인의 현재 상태를 조합하는 정책 기능이다.

- 경기의 종료 여부와 종료 시각
- 신고자와 대상의 참가 확정 이력
- 신고자와 대상의 동일인 여부
- 동일 관계의 기존 신고 여부
- 관리자의 검토 상태

따라서 Controller의 입력 검증만으로 해결할 수 없다. 요청 DTO는 형식과 길이를 검증하고, 서비스는 여러 저장소가 필요한 유스케이스 규칙을 검증하며, 엔티티는 자신의 상태 전이를 보호하는 방식으로 책임을 나눈다.

---

## 2. 최종 신고 정책

1. 종료된 경기만 신고할 수 있다.
2. 경기 종료 후 7일 이내만 신고할 수 있다.
3. 신고자는 해당 경기의 `ACCEPT` 참가자여야 한다.
4. 신고 대상도 해당 경기의 `ACCEPT` 참가자여야 한다.
5. 자기 자신은 신고할 수 없다.
6. 중복 기준은 `경기 + 신고자 + 신고 대상`이다.
7. 서로 다른 사용자가 같은 대상을 신고하는 것은 허용한다.
8. 신고 유형은 `POOR_SPORTSMANSHIP`, `NO_SHOW`, `ABUSIVE_LANGUAGE`이다.
9. 내용은 필수이며 최대 500자이다.
10. 관리자는 승인하거나 거절하고, 승인과 제재는 분리한다.

이 정책에서 참가 상태는 현재 참가 여부가 아니라 경기에 실제로 함께하기로 확정됐던 관계를 나타낸다. 경기 종료 후 신고를 받으므로 단순 사용자 검색보다 경기 참가 이력을 근거로 삼는 것이 중요하다.

## 3. 시간 경계와 `Clock`

“7일 이내”는 정확한 경계를 코드로 정의해야 한다.

```java
LocalDateTime deadline = gameEndedAt.plusDays(7);

if (reportedAt.isAfter(deadline)) {
    throw new CustomException(REPORT_PERIOD_EXPIRED);
}
```

이 조건은 종료 후 정확히 7일인 시각은 허용하고, 그보다 1나노초라도 늦으면 거절한다. 요구사항이 “7일째 23:59:59까지”라면 날짜 기준 정책으로 다시 정의해야 한다.

서비스에서 `LocalDateTime.now()`를 직접 호출하면 테스트 결과가 실행 시각에 의존한다. `Clock`을 주입하면 운영에서는 시스템 시각을 사용하고 테스트에서는 고정 시각을 주입해 종료 전, 정확한 경계, 경계 초과를 반복 가능하게 검증할 수 있다.

---

## 4. 검증 순서의 의미

검증은 단순히 모든 `if`를 나열하는 작업이 아니다. 다음을 고려한다.

- 가장 명확하고 저렴한 오류를 먼저 발견하는가?
- 이후 조회가 성립하기 위한 전제조건을 먼저 확인하는가?
- 예외 우선순위가 API 사용자에게 자연스러운가?

현재 흐름은 자기 신고 여부, 경기 존재, 신고 기간, 신고자 존재와 참가 자격, 대상 참가 자격, 대상 사용자, 중복 순으로 진행된다. 중복 검사보다 참가 자격을 먼저 확인하므로 권한이 없는 사용자가 기존 신고 존재 여부를 추측하기 어렵다.

검증 순서는 외부 계약의 일부가 될 수 있다. 동시에 여러 조건이 잘못됐을 때 어떤 예외가 먼저 반환되는지 테스트와 API 문서가 일관되어야 한다.

---

## 5. 상태 머신과 엔티티 책임

신고 상태는 다음 단방향 전이를 가진다.

```text
             ┌─→ APPROVED
PENDING ─────┤
             └─→ REJECTED
```

`APPROVED`나 `REJECTED`에서 다시 다른 상태로 변경하는 정책은 없다. 이 규칙은 `ReportEntity.approve()`와 `reject()` 내부의 `validatePending()`이 보호한다.

상태 전이를 엔티티에 둔 이유는 서비스가 여러 개 생겨도 동일한 불변식을 우회하지 못하게 하기 위해서다. 서비스는 “누가 어떤 신고를 검토하는가”를 조율하고, 엔티티는 “현재 상태에서 이 전이가 가능한가”를 판단한다.

관리자 검토에는 처리 관리자, 처리 사유, 처리 시각을 함께 저장한다. 상태만 변경하면 나중에 왜 그렇게 판단했는지 추적할 수 없다.

## 6. 중복 방지와 경쟁 조건

서비스의 `exists` 검사만으로는 동시 요청을 완전히 막을 수 없다.

```text
요청 A: exists=false
요청 B: exists=false
요청 A: INSERT
요청 B: INSERT
```

두 트랜잭션이 INSERT 전 동일한 결과를 봤다면 중복 행이 생길 수 있다. 따라서 다음 두 계층을 함께 사용한다.

- 서비스 사전 검증: 이해하기 쉬운 도메인 예외를 반환한다.
- DB 유일 제약조건: 경쟁 조건에서도 중복 저장을 최종 차단한다.

유일 키가 `신고자 + 대상 + 경기`인 이유는 동일 경기에서 동일 관계의 반복 신고만 금지하기 위해서다. 신고자가 다르면 별도의 관찰과 피해일 수 있으므로 허용한다.

실무에서는 유일 제약조건 위반 예외를 도메인 중복 예외로 변환하는 처리도 검토한다.

## 7. 신고 승인과 제재 분리

승인은 “신고 내용이 타당하다고 판단했다”는 의미이고, 제재는 “서비스 이용을 일정 기간 제한한다”는 별도의 행위이다.

분리하면 다음 장점이 있다.

- 승인된 신고라도 상황에 따라 경고만 할 수 있다.
- 향후 제재 종류와 기간을 별도로 확장할 수 있다.
- 신고 검토 관리자와 제재 결정 관리자를 추적할 수 있다.
- 신고 건수만으로 자동 제재하는 오탐 위험을 줄인다.

단점은 관리자 작업 단계가 늘어난다는 것이다. 운영 효율이 중요해지면 승인 화면에서 제재 생성 화면으로 연결하되 도메인과 데이터는 계속 분리할 수 있다.

---

## 8. 단위 테스트와 통합 테스트의 역할

단위 테스트는 Mock 저장소와 고정 `Clock`으로 분기와 협력 객체 호출을 빠르게 검증한다.

- 신고 성공 시 어떤 값으로 저장하는가?
- 자기 신고, 미종료 경기, 기간 초과를 차단하는가?
- 두 참가자가 모두 `ACCEPT`여야 하는가?
- 상태 전이가 올바르고 반복 처리를 막는가?

통합 테스트는 실제 MySQL과 JPA를 사용해 단위 테스트가 확인하기 어려운 부분을 검증한다.

- 연관관계와 enum이 실제로 저장되는가?
- 유일 제약조건이 기대한 조합에 적용되는가?
- 서로 다른 신고자는 동일 대상을 신고할 수 있는가?
- 상태별 Page 조회와 정렬이 실제 쿼리에서 맞는가?
- Dirty Checking으로 검토 결과가 반영되는가?

통합 테스트에서 `flushAndClear()`를 사용하면 영속성 컨텍스트의 같은 객체를 다시 읽는 착시를 제거하고 실제 DB 반영과 재조회 매핑을 검증할 수 있다.

## 9. 면접 질문과 답변 포인트

### 왜 종료된 경기만 신고하나요?

진행 중 분쟁을 신고로 확정하기보다 실제 참가 관계와 경기 종료를 기준으로 사건 범위를 고정하기 위해서다.

### 왜 7일 제한을 두나요?

지나치게 오래된 사건의 사실 확인 비용을 제한하고 운영 처리 가능한 기간을 명확히 하기 위해서다.

### 왜 엔티티에서도 검증하나요?

상태 전이는 객체 자체의 불변식이므로 어느 서비스에서 호출하더라도 우회되지 않아야 한다. 여러 저장소가 필요한 자격 검증은 서비스에 둔다.

### 왜 DB 유일 제약조건도 필요한가요?

사전 조회와 저장 사이의 동시성 경쟁을 애플리케이션 검사만으로 막을 수 없기 때문이다.

### 승인 즉시 블랙리스트 처리하지 않은 이유는 무엇인가요?

신고 사실 판단과 이용 제한이라는 제재의 의미 및 운영 책임을 분리하기 위해서다.

## 10. 추가 개선 과제

- 관리자 두 명이 같은 신고를 동시에 검토할 때의 낙관적 락 또는 조건부 UPDATE
- 첨부 증거와 개인정보의 보관·삭제 정책
- 신고 취소와 사용자 자신의 신고 처리 현황 조회
- 신고 목록의 연관 엔티티 조회 시 N+1 측정
- 관리자 역할 세분화와 감사 로그
- 다수 신고를 사건 단위로 묶는 모델

기술은 필요성보다 먼저 도입하지 않는다. 동시 검토 충돌, 목록 조회 병목, 운영 감사 요구를 측정하거나 확인한 뒤 적절한 해결책을 선택한다.
